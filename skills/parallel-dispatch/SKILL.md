# 并行分派规范

## 何时使用

**适用场景：**
- 3个以上测试文件因不同根因失败
- 多个子系统独立出现故障
- 每个问题无需其他问题的上下文即可理解
- 排查之间无共享状态

**不适用场景：**
- 失败是相关的（修复一个可能修复其他的）
- 需要理解完整的系统状态
- 智能体之间会互相干扰

## 决策流程

```
存在多个失败? → 是 → 它们是否独立? → 是 → 能否并行工作? → 是 → 并行分派
                          ↓否                ↓否
                   单个智能体排查      顺序执行智能体
```

## 分派前自检清单

- [ ] **失败已量化**：已统计失败数量和类型，确认 ≥3 个独立失败
- [ ] **关联性已排除**：快速扫描错误信息，未发现共同根因
- [ ] **资源已评估**：当前可用并行 slot ≥ 需要的分派数量（最大并行 ≤5）
- [ ] **上下文已收集**：每个失败的关键日志、涉及文件、预期行为已提取

## 工作流程

### 前置检查

**输入**：失败列表（包含错误日志、测试报告、涉及文件路径）
**动作**：
1. 统计失败数量和类型（<3个时建议顺序处理）
2. 快速扫描错误信息，判断是否有相同根因
3. 如果失败高度相关 → 进入单一智能体排查流程

**输出**：失败数量统计、关联性评估、建议的分派方案

### 1. 识别独立的问题域

**输入**：失败列表、错误日志
**输出**：独立问题域分组方案

分组原则：
- 同一子系统/模块的失败归为一组
- 涉及相同代码文件的失败归为一组
- 错误信息中包含相同关键字的失败可能相关

### 2. 创建聚焦的智能体任务

每个智能体获得的结构化任务描述：
```markdown
### 任务：{具体目标}

**问题域**：{测试文件/子系统名}
**上下文**：
- 失败信息：{关键错误日志}
- 涉及文件：{文件列表}
- 预期行为：{正确行为描述}

**约束条件**：
- 只修改 {指定范围} 内的代码
- 不要修改其他智能体负责的文件

**预期输出**：
1. 根因分析（2-3句话）
2. 修改内容摘要（列出修改的文件和行号）
3. 验证结果（测试是否通过）
```

### 3. 并行分派

将各任务分派给独立的上下文执行，确保任务之间互不干扰。

### 4. 审查与集成

- 阅读每个总结
- 验证修复之间没有冲突：
  1. **文件重叠检查**：列出各智能体修改的文件清单，比对是否有交集
  2. **代码冲突检查**：对冲突文件，比对修改的行号范围
  3. **回归验证**：运行完整测试套件
- 集成所有更改

## 常见错误

| 错误做法 | 正确做法 |
|---------|---------|
| 太宽泛："修复所有测试" | 具体明确："修复 agent-tool-abort.test.ts" |
| 无上下文："修复竞态条件" | 提供上下文：粘贴错误信息和测试名称 |
| 无约束：智能体可能重构所有代码 | 设置约束："不要修改生产代码" |
| 模糊的输出要求："修好它" | 明确要求："返回根因和修改内容的总结" |

## 执行约束

- **最大并行数**：不超过 5 个智能体同时运行
- **超时设置**：每个智能体任务建议设置 10-15 分钟超时
- **失败回退**：任一智能体失败时，收集已完成的成果，失败任务降级为顺序处理

## 异常处理

| 场景 | 处理策略 |
|------|---------|
| 失败可能相关 | 重新评估关联性；放弃并行改为单一智能体排查 |
| 智能体之间出现冲突 | 检查冲突文件范围，优先保留业务逻辑正确的修改 |
| 智能体返回结果质量不足 | 要求补充上下文；转交另一个智能体 |
| 资源限制无法并行 | 降级为顺序执行 |
| 智能体超时未返回 | 标记超时，收集已完成结果，对超时任务单独处理 |

## 验证 checklist

- [ ] 已确认失败之间确实独立
- [ ] 每个智能体任务范围清晰、自包含
- [ ] 已设置约束条件（不修改其他智能体负责的文件）
- [ ] 已明确预期输出
- [ ] 集成前检查了修改冲突
- [ ] 运行了完整测试套件验证
